# 学习计划重构：需求底稿与外部评审说明

整理日期：2026-10-23。用途：供学习者、当前教师和其他AI共同评审，作为分块重构的输入。

状态：需求与事实底稿；已综合三轮评审、实际代码和用户确认形成v2.1执行路线。文中明确区分用户需求、已观察事实、历史方案和待决策事项；其他AI的建议须与这些内容核对后再采用。

## 先读这一页摘要

学习者是在校生，预计2029年毕业，有Python基础，希望形成全栈开发与AI应用工程能力，并逐步具备参与实习、独立完成和维护软件的能力。关注广州、深圳、上海及沿海城市的机会，也愿意长期拓展技术广度。本轮直接确认AI应用全栈优先、2027年10月前后准备投递、计划每周十几小时，以及公开演示/私人隔离方案。

学习者目前最明确的教学选择：先知道系统整体如何组成、数据和职责放在哪里，准备最小可运行骨架，再在骨架中学习简单功能，逐步补齐复杂实现。讲新知识要通俗、完整、结合自己的项目；已会的相同写法应合并练习。核心功能希望自己组织，允许查资料和使用AI，卡住时逐级帮助。

长期主作品是私人美股双账户只读看板，对比本人实盘与外部AI操作的模拟盘。网站负责读取、保存、展示和分析，交易执行在外部。作品需要逐步形成页面、数据库、接口、权限、部署、数据导入和有来源的AI复盘。真实券商读取与自动同步尚未验证，现有代码只用演示数据。

旧课已经完成学习记录工具和Vue演示看板，但多数功能经提示或示范完成。运行成果与独立能力分别记录。原九章46阶段曾在v2.0重组为七章28阶段；最终v2.1为七章29阶段，类型学习从第2章移至单独的4.1，现有代码复用；重组不表示课时缩短或已独立掌握，新数据库/权限/模型功能仍未实施。

本次重构要先稳定目标与需求，再审架构、能力路线、教法与执行机制。模型能力变化可影响教师和AI的辅助方式；课程取舍要依据实际能力缺口、项目需求、技术变化和岗位证据，留下变更理由。

## 1. 用户已表达的学习需求

### 1.1 希望达到的能力

- 理解一个实际需求怎样变成可运行的软件，能解释系统整体分工和完整数据流。
- 学会前端、后端、数据库的合作，逐步能自己修改功能、排查问题、验证结果和维护运行。
- 能使用AI编程工具，也能检查其产出、定位改动、发现问题并承担验证责任。
- 将来能构建LLM/AI应用，理解它怎样接入业务、使用数据、处理失败及核对输出。
- 学习成果能够支持实习准备，并能向别人说明自己的项目、贡献和实际掌握程度。
- 在有主线的同时逐步增加技术储备，避免长期只依赖一个工具或单一技术。用户愿意多学，不希望因“AI能代写”而跳过理解。
- 获得持续自学与迁移能力：工具或模型变化后，能读文档、比较方案、理解陌生代码并继续完成需求。

这些是能力目标。最终技术栈、章节数、是否学习某个具体框架，属于实现这些目标的方案。

### 1.2 时间、环境和就业背景

- 预计2029年毕业；具体年级、学校课程和目标岗位细分仍可在需要时补充。
- 用户已直接确认计划每周十几小时，约40分钟作为参考课段。空闲时可以连续学习，疲劳时只学一段；每日时间不固定，有效投入需实际记录。
- 用户明确要求由自己决定什么时候停止，不在40分钟时自动结束；连续学习也要交代课段边界。
- 已有Python基础，近期重点是全栈与AI应用。会哪些语法不能直接推出能独立交付项目。
- 目前在Windows和VS Code中学习。换电脑曾讨论，尚不是课程实施前提。
- 实习关注广深沪及沿海城市，优先AI应用全栈，目标2027年10月前后准备投递。企业类型、具体年级和实习出勤资格仍需核实；这是准备窗口，不是获得offer的承诺。
- 累计有效学习时间未可靠统计，不据聊天跨度估算“还需多少天出师”。

## 2. 主作品需求：私人美股双账户看板

以下从已有需求草案和用户确认的项目目标提炼，独立于Vue/FastAPI等技术选择。

### 2.1 用户、用途和边界

- 比较本人操作的IBKR真实资金账户与外部AI操作的IBKR模拟账户。
- 主要供本人使用，先本人登录；额外一至两位查看者按实际需要增加。
- 有固定网址，手机、平板、电脑可访问，日常使用不依赖个人电脑开机。
- 已认可公开演示版与私人真实版共用代码、隔离配置/数据/凭据；公开只展示虚构资料，不能访问私人数据库或真实券商。是否公开源码另行决定；方案认可不表示已发布。
- 网站负责读取、保存、展示和分析。下单、撤单、转账、修改券商账户及AI自动交易执行不属于本网站范围。
- 假数据明确标注；实际账户信息、行情和AI日志的可得性逐项验证。

### 2.2 逐步形成的功能

| 功能 | 用户希望获得什么 | 需保留的边界 |
| --- | --- | --- |
| 双账户总览 | 净值、现金、账户类型、币种、来源时间和数据状态 | 明确实盘/模拟盘，演示与真实资料分开 |
| 持仓 | 股票、数量，逐步加入成本、市值、盈亏、占比 | 实际字段及估值来源需核对 |
| 交易记录 | 成交时间、方向、数量、价格、费用及筛选 | 当前持仓与历史成交分别保存和解释 |
| 历史与比较 | 查看不同时点变化，逐步比较收益及回撤 | 先统一时间、区间、币种、费用与资金流口径 |
| 私人访问 | 本人登录、账户归属检查，按需分享查看 | 前端隐藏按钮不足以落实后端访问控制 |
| 复盘 | 当时的AI决策日志、资料、成交与后续分析可追溯 | 缺少原始理由就标缺失，事后分析说明性质 |
| 持续使用 | 数据导入/更新、失败和过期提示、日志、备份恢复 | 保留上次正确结果，能定位问题和恢复 |

近期可演示版本以双账户总览、持仓、来源时间和加载状态为核心，再形成保存、本人权限与私人部署。收益曲线、真实同步和AI复盘按数据条件逐步实现。

### 2.3 数据与比较要求

- 数据能够识别所属账户、对应时点、币种、来源及收到时间。
- 历史记录能够追溯，不把页面刷新时间当作券商估值时间。
- API金额、价格和数量采用精度可保留的表示；现有演示使用十进制字符串。正式计算与保存方案在实现时验证。
- 缺失、过期、估算和真实的零有区别，页面反馈要明确。
- 比较收益要处理入出金、费用、分红、汇率、已有持仓及模拟盘重置；金额增加不能直接当作投资盈利。
- 模拟与真实账户的成交/费用条件可能不同，比较结果要说明限制。
- 相同记录重复导入、部分失败和修正有可核对的处理方式与来源记录。

### 2.4 数据取得、权限与运行

- 先用演示数据和可追溯文件导入；分别验证两账户可用的读取方式、字段、历史覆盖、授权、会话与频率。
- 自动同步暂不可用时，保留文件导入的实用版本，明确更新时点和限制。
- 券商读取授权、行情订阅和显示许可分别核对；不能从“能看见页面”推出“接口可自动读取”。
- Bot只获得必要的数据提交能力，结构、账户、时间和重复记录由服务器校验；代码维护、服务器管理与交易权限另有边界。
- 凭据留在受控配置或授权流程中，前端和仓库不包含真实秘密；实际资产资料和测试素材隔离。
- 固定网址、HTTPS、服务启动、日志、备份、实际恢复和回退逐步落实。
- 优先评估已有日本VPS能否承载及是否影响既有用途，具体资源与可用性尚未验证。
- 同步频率、行情、域名、服务器及模型费用等待实际核查；历史草案中的秒级频率是设想，不是保证。

## 4. 用户明确的教学要求

### 4.1 先有整体骨架，逐步学实现

- 新功能先说明真实使用场景、系统分工、数据归属和完整流转，再定位本次学习部分。
- 希望提前确定最小结构，先跑通简单完整功能，复杂实现逐步补到相应位置。
- 演示业务数据放在对应的后端/数据库位置；前端接住返回数据、记录界面状态、由组件显示。
- 教师可准备必要支架，解释贡献和限制；学习者逐步理解并实现核心查询、业务和页面连接。
- 现有项目和成果可以继续使用，避免为教学反复移动数据职责、重新写相同功能。
- 当前需要多少目录/文件就解释多少，暂时用不到的复杂模块先在图上说明用途。

### 4.2 讲解和任务颗粒度

- 使用通俗中文解释，代码标识、注释与显示字符串使用英文。
- 新名词、API或语法在使用前解释：是什么、谁执行、输入是什么、返回什么、为什么与当前功能有关。
- 从完整的实际数据结构解释到中间结果和显示，不省掉嵌套层级或把一半写法留给学生猜。
- 优先使用自己的账户例子；类比要落回实际代码。
- 相同已会写法的多个字段/操作合并布置，避免每一行都单独等待回复。
- 新机制按理解拆开，熟悉内容可一次完成一个有意义的目标。
- 每次解释或补讲后，都交代实际任务、主要文件和完成现象，不能只解释用法后漏掉任务。
- 教师读取真实保存文件检查；学生发“1”表示提交检查或继续，不等同于掌握证明。

### 4.3 从理解走向自己组织

- 已会的写法先给目标、约束和验收现象，让学生可查旧代码/资料后尝试。
- 新用法先讲清并完整示范必要局部，再给同类的小变化；避免始终整题照抄。
- 卡住时按思路/位置、相关API、局部示范逐级帮助，明确不会时及时换具体例子。
- 用户明确要求完整示范时可以提供，并如实记录帮助。
- 用实际需求变化观察迁移能力，不强制默写、无提示倒计时或频繁额外考试。
- 教师准备、提示后完成、独立完成和实际验证分别记录。后续复用同类功能时观察是否少依赖提示。

### 4.4 节奏与记录

- 约40分钟是参考课段，连续学习时有明确边界，用户决定何时停止。
- 开始当天学习时给出连贯目标和合理分量，下一段有衔接。
- 阶段收尾报告本章成果进度，同时说明理解和帮助程度。新计划可重新划分阶段，已完成成果不能被抹掉。
- 允许长时间停课，回来按当前停点恢复，不因记忆生疏自动重学整章。
- 课后按已有授权在约定私有GitHub仓库归档代码、计划、实际学习内容和未来两三次安排，供其他AI监督；不能假定其他AI已获得访问权限或已读过。
- 日期、有效课时和验证来源按事实记录；没有计时就说明未知。

## 5. 稳定目标与可变方案

| 层面 | 内容 | 调整依据 |
| --- | --- | --- |
| 相对稳定的目标 | 能理解并交付软件、实习准备、AI应用与长期迁移能力 | 用户目标或现实约束发生实质变化 |
| 相对稳定的产品需求 | 私人只读双账户看板、历史可追溯、权限、可信比较与维护 | 真实使用反馈、数据可得性及业务范围变化 |
| 当前技术方案 | Vue/FastAPI/SQLite，后续TS/服务端数据库/第二语言等 | 岗位样本、项目约束、实际维护及学习成本 |
| 教师和AI的分工 | 支架准备、提示方式、审查、验证与工具辅助 | 模型能力、学生独立表现、工具可靠性 |
| 日常安排 | 一次任务大小、例子、复习时机和课段数 | 当次理解、精力与真实卡点 |

用户愿意随模型和技术进步调整方案，也希望课程保持连续。建议把一次变更写成：改变原因、证据、影响范围、复用的已有成果、观察效果的时机。v2.1采用章末或约两个月复盘，并在明确阻碍出现时处理；日常先调整解释和任务大小，具体变更仍需留下上述依据。

新工具发布或模型升级，可以先影响辅助方式；是否改变技术主线和课程取舍，需要说明它怎样改善用户的实际目标。技术广度是明确诉求，应讨论先后和深度，不默认只学一套，也不同时强塞多套。
