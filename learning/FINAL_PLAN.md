## 一、目标与约定

- 优先AI应用全栈：理解需求，组织前端、后端、数据库、模型和运行维护，能解释、修改、验证并交付小功能；长期增加技术广度和自学迁移能力。
- 预计2029年毕业，目标2027年10月前后准备投实习，关注广深沪及沿海城市；具体届别资格、到岗天数与开放岗位按实际核实。
- 每周计划十几小时，约40分钟为参考课段，用户决定停止。一个阶段可跨多课；先记录实际投入与帮助，再校准窗口。
- 主作品为私人美股双账户只读看板，公开虚构演示版与私人真实版共用代码，隔离配置、数据库和凭据。网站读取、保存、展示与分析，交易执行在外部。
- 先确定全产品的简单分工图、数据归属、主要连接和待验证依赖，再建立最小可运行链路；学生在同一系统里完成真实功能，教师在需要时讲知识、准备必要支架并标注贡献。既有组件、接口和查询直接接续。
- 每项新机制先解释用途、执行者、输入、中间值和结果；熟悉同类改动合并任务。允许查资料与AI，评价学生的组织、判断和验证能力。

招聘目标、作品功能和教学节奏一起决定取舍。技术栈、章节数和月份是实施方案；已有成果与能力证据保留。当前不追求一次列完所有技术，按具体用途逐步增加。

### 一年两款实战产品（2026-10-27目标校准）

用户明确希望一年做出两个实战产品。规划窗口为2026年10月至2027年10月；这是交付目标，具体用时用实际课段校准。公开演示版和私人版属于同一个产品，不重复计数；第二款必须有不同的真实使用需求，不是换皮或照抄教程。保留七章与既有进度，调整交付顺序和时间分配。

- 产品一：美股双账户只读看板。首个可交付版本包含总览/持仓/历史曲线、统一UI与手机适配、备注管理、至少一种有用途的数据录入路径、有来源的AI复盘、与发布范围匹配的访问控制及隔离、部署/日志/备份恢复。虚构演示可独立展示，真实券商接入按验证结果推进，不让复杂金融口径或自动同步卡住交付。
- 产品二：在第一款核心版本稳定后，选另一个本人或少量真实使用者有需求的产品，由学生逐渐主导需求、数据结构、接口、界面、排错和上线。允许沿用主栈、查资料和AI；教师对新机制继续带写，对反复实践的部分减少提示。题目与功能范围届时确认，不现在凭空定项目，也不以第二语言作为开工前提。
- 产品交付证据：核心用户流程能完整使用，有清晰界面/必要移动适配、持久化和适当错误反馈、可访问演示或适合目标用户的实际运行环境、可复现说明和必要验证，并至少经历一轮真实使用反馈后的修改。第二款不是所有环节完全无帮助；记录学生选择与AI/教师贡献。
- 近期顺序：已完成备注和单份虚构快照写入演示；用户希望历史曲线等真实数据可用后再考虑，真实来源与同步规则先按可得资料核实。下一步讨论AI复盘用途与输入输出，先用虚构资料；第4章交付前再系统打磨界面/状态。净值趋势与扣除资金流影响的收益比较分开，后者在6.4按资料条件完善。
- 时间分配先按前6个月完成第一款核心交付、随后约5个月完成第二款并迭代、末1个月留测试/使用反馈/材料缓冲。第一款交付后以维护和必要改进为主；第6章复杂真实同步、金融统计及7.4技术广度按用途穿插或后置，不占用全部第二产品时间。每章/约两个月复核，进展快前移，不把窗口当保证。
- 7.1项目材料和7.2岗位核对持续穿插；7.3第二款产品从可选练习提升为年度交付目标。并不要求学完七章才启动第二款，也不要求两款都堆同样的全部技术。



## 二、全系统分工图

2026-10-27，v2.2配套。先看全产品位置，再对照正在实现的实际链路；未实现部分不建空目录。

```text
IBKR／实际报表／演示种子
          ↓
接入：获取、检查、转换、记录来源 ──→ 数据库
                                          ↕
浏览器操作 → Vue请求 → FastAPI查询/处理 → 组织回复
页面显示   ← 组件     ← Vue保存收到的数据和界面状态

AI：后端取得有来源资料 → 调用模型 → 检查并存库 → 页面
身份/归属：后端检查请求者能做什么、能访问哪些记录
运行维护：部署、服务、日志、备份和实际恢复
```

| 部分 | 负责及交付 | 目前位置/状态 |
| --- | --- | --- |
| 数据来源/接入 | 将外部记录检查转换为内部记录，保存来源/时点并报告失败 | scripts/prepare_demo_database.py仅演示种子；IBKR、文件接入及其能力尚未验证 |
| 数据库存储 | 保存账户、各时点快照、该时点持仓；以后增加备注和复盘 | data/dashboard.db，快照note列保存单条备注，持仓关联快照；旧notes表暂保留未关联数据 |
| 后端 | 查询、业务校验、组织回复；以后检查身份、归属并协调AI | 根main.py；read_account(account_id)查询两账户基本资料、最新快照和全部持仓，/accounts返回列表；未知账户/缺快照404 |
| Vue状态/请求 | 接住后端数据，管理选择、等待和错误 | frontend/src/App.vue；初始null并自动加载，按account_type分配；computed.current_account驱动同一套组件，响应式脚本/构建已验证 |
| 组件 | 接收字段显示，向上报告用户操作 | 既有标题、概览、选择、持仓、提示组件继续使用 |
| AI/权限/运行 | 在后端控制调用/访问；为全系统提供持续运行能力 | 后续模块，尚无模型、登录或部署成果 |

第一版目标：双账户总览、完整持仓、历史变化、来源与时点说明。当前总览/持仓/来源时间已显示；通用/accounts/{account_id}/snapshots已真实验证，AccountHistory已显示历史并在切账户时自动重新取数。快照单条备注显示、增改删及隔离验证已完成，旧备注表/接口待整理；精确停点见STATUS。此处调整产品先后，不重置既有章节或重建项目。

接口约定就是后端交给页面的数据样子。当前完整账户目标见[实际数据库与返回样例](learning/DATABASE_MAP.md)；先沿用既有name/netvalue/holding等键，金额/数量为十进制字符串。Vue保存回复副本不等于承担持久保存。

需要核对：IBKR两种账户分别能取得的字段、时间、历史、授权及更新条件。接入侧转换用于减少影响，真实业务差异仍可能改变表/接口/页面。第1章期间开始准备最小样本核对，2.3定设计前记录结论；拿不到样本就标未知，演示照常建设。

课堂先看本图及当前实际数据，直接实现完整目标。教师准备必要支架，学生组织核心连接；新知识在用到时解释，基础卡点原位补清，提示按表现减少。

#### 第1章：稳定骨架与数据库链路

| 阶段 | 做什么 | 完成证据 |
| --- | --- | --- |
| 1.1 全图与运行入口 | 明确全系统分工及当前缺口，对照App.vue/main.py追踪请求；沿用本项目独立环境和运行入口 | 能指出主要文件、数据去向和服务地址；在学生实际终端完成启动/查看日志，支架与帮助另记 |
| 1.2 单表查询到快照接口 | 教师准备最小SQLite演示支架；学生先查询snapshots的一条/多条记录，再用account_id参数筛选，最后组装既有快照返回 | `/accounts/paper/snapshots`真实返回来自库的数据，字段不变；正常/无匹配有明确结果，可解释参数和一条返回值 |
| 1.3 完整账户接回页面 | 实现数据库双账户最新状态与持仓到现有页面；沿实际实现观察中间值，组装/accounts原结构 | 页面显示库中数据；初始未加载/加载/空/失败可见，切换仍可用，重复前端资产样本整理完成 |
| 1.4 一次端到端变化 | 从已经接通的数据中选一个小需求，如显示一个字段或查询已有时点 | 给目标和验收后可查资料组织，说明修改位置；验证正常和一个相关边界，记录实际帮助 |

1.2按“打开连接和确定文件→查询并看结果→按条件筛选→将行变成字典→接入路由”逐次讲，不同时要求掌握JOIN、对象嵌套、序列化和新抽象。使用现有`demo_paper`及`netvalue`，参数化查询按实际输入演示，连接关闭及错误处理讲清。教师可准备连接/路径支架，学生逐步理解；不得声称尚未准备的库已经存在。[Python sqlite3参数绑定](https://docs.python.org/3.14/library/sqlite3.html#how-to-use-placeholders-to-bind-values-in-sql-queries)。

以下为第1章已走过的实现顺序；当前事实和停点以交接页为准：

1. 从已有基本资料查询继续，依次查询最新快照及该快照持仓，组装完整模拟账户；单行取下标前检查结果是否存在，全部所需查询结束后关闭连接。
2. 完整模拟账户验证通过后，用account_id参数复用查询与组装，读取实盘账户；保持/accounts的现有键名及模拟盘、实盘返回顺序。
3. 先验证完整接口回复，再改Vue的未加载、加载、空、失败状态与显示条件，并清理重复初始资产；最后验证页面切换和显示。
4. 通过后进入1.4，用一次自然需求变化观察迁移，允许参考旧代码。课堂可跨多课，始终完成同一个目标；新知识出现时就地解释。


1.3使用前约定：账户不存在的404及detail、缺快照与空持仓的不同含义、数据库异常与前端反馈；保留现有框架错误并检查前端能处理的实际形状，不搭通用错误框架。涉及金额计算前核对十进制精度/舍入，时间查询前核对时区和最新的含义；现有快照是带时区的演示时点，未验证真实交易日。第1章阶段收尾复用一次学生自己说明数据从哪里来、经过谁、显示在哪的证据，允许看资料，不每次提交考试。

#### 第3章：最小AI复盘

| 阶段 | 做什么 | 完成证据 |
| --- | --- | --- |
| 3.1 一次真实模型调用 | 后端发送少量虚构记录，页面显示简短回复；先讲请求/上下文/模型/返回的对应关系 | 实际可用API或模型服务完成调用，凭据仅后端；记录模型、用量及输入来源，限制输入/输出和重复请求 |
| 3.2 有来源并可保存的输出 | 约定摘要、引用标识和资料不足状态，检查结构及引用，再存SQLite并读回 | 刷新/重启仍能看到结果及原资料引用；原始日志与事后分析分清，引用存在不等于结论正确 |
| 3.3 失败与成本 | 处理超时、限额、无效输出、重复点击和受控重试 | 有反馈、保留账户数据；服务器落实调用次数/并发或预算上限，日志可定位且不泄露凭据 |
| 3.4 固定样本核对与小变化 | 用少量有据/无据/缺失材料核对内容，再变更一个小目标 | 能解释输入、输出、失败和判断错误的依据；模型停用不影响账户展示和已保存记录 |

## 七、教学方式

### 七条教学原则

| 原则 | 正例 | 应避免的例子 |
| --- | --- | --- |
| 1. 每次教学先定位当前这一步 | 每次讲解、补讲、检查后继续或布置任务，先简短说清正在实现的功能、本步用途、数据从哪里来、接下来交给哪个函数/模块、完成后能看到什么；新功能给全图，同功能用短链路标出当前位置；临时素材说明后续接入位置 | 只给语法和修改步骤，持续添加字段；迁移数据/拆组件前没说清整体去向，让学生感觉完成后又推倒重来 |
| 2. 把输入、执行机制和结果讲完整 | 用当前代码的具体值说明谁触发、按什么条件判断、依次执行什么、哪些状态独立保存、修改前后结果如何变化；例如解释key时走完组件复用/重建与mounted的过程 | 只解释名词、给比喻或说“会自动”，就直接布置修改，等学生追问才补因果过程 |
| 3. 新名词和语法在使用前解释 | 说明src是脚本来源、浏览器何时加载，再让学生添加；“底层逻辑”先落到谁执行、处理什么值、按什么顺序、为什么有这个结果 | 提过API名称就默认会用，或从当前任务岔开讲大量底层实现 |
| 4. 新内容先讲清并带着写 | 学生没写过或仍生疏的内容，先解释用途与执行过程、给完整局部示范，再一步步带写当前功能 | 把看过、抄过或只带写过一次当成已会，立刻布置独立整段任务；为避免给答案而省略必要指导 |
| 5. 按理解调节跨度 | 同一种已会写法的字段或操作合成一个任务，先解释各项用途，再一次完成和检查；陌生机制分步讲，新工程先固定主要编辑文件 | 把account_id和as_of等相同显示写法拆开反复等1，或一次引入多个陌生机制；跨文件做无关练习 |
| 6. 结果、理解和帮助分别记录 | 标出接口验证和一次小改动需要几次提示 | 把运行成功、截图或回复1直接记为独立掌握 |
| 7. 熟悉且愿意尝试时再自主写 | 学生自己写过很多次或教师反复带写、本人想尝试独立组织时，只给完整目标和少量提示，允许查旧代码；卡住再逐级增加帮助 | 默认所有任务都先独立尝试，或熟悉内容仍逐行给答案；把一次示范、运行成功或回复1作为切换独立任务的依据 |

每完成一个有意义的功能步骤，适时请学生先想一想下一步做什么或有什么想补充的，再给出教师建议、理由和取舍，共同决定方向；学生想先听建议或不想回答时直接指导，不把交流变成考试。同一功能中的小方向改错、相关熟悉写法和可一起检查的修正集中讲解并一次完成，不逐个询问、不拆成多轮确认；涉及生疏机制先解释清楚。在真实功能的重要设计或体验选择上主动邀请学生提出想法、补充需求或比较方案；新知识仍先解释并带写，熟悉内容给适当空间。问题自然融入开发，学生已表达的决定不反复确认。新功能动数据库或接口前，先和学生讨论真实使用方式、页面交互、关键数据关系和数量限制，学生可提出偏好，教师主动说明方案与风险并形成共同方向；未知细节按需渐进，不为猜测提前定型。学生明确希望教师敢于质疑：发现需求假设、方案或代码的问题时，应主动说明具体风险和成本，提出有理由的建议或替代方案；不同意时明确说出，不迎合、不假装存在脱离实际条件的唯一最优解。核心产品取舍由学生知情参与。

帮助方式以实际练习经历和学生意愿判断：没写过、没正式学过或仍不熟的内容，一步步讲解并带着写；自己写过很多次或教师带写多次、学生想尝试时，再改为给任务和小提示。见过示例、文件里出现过、抄过或只运行成功过，都不足以判定可以独立写。拿不准时默认带着起步，不让学生反复声明自己没学过；自主尝试遇到新内容时及时恢复讲解和带写。首次测试例子也说明：由谁在哪里输入、为什么选它、要观察什么。一次讲解对照当前文件、触发动作、值的变化和显示位置；比喻要落回代码。用户要求完整示范时照做并记录示范帮助。

### 先定骨架，在固定分工里逐步学习

执行顺序：先对照[全系统地图](../ARCHITECTURE.md)，再在现有项目持续完成一个真实功能；局部补基础服务当前任务。本轮取舍见[教学评审整合](TEACHING_REVIEW_DECISIONS_2026-10-24.md)。最初两三课试用后，用实际位置感、组织/排错和帮助变化校准；不以更换模式本身认定有效。

先确定全产品的简明地图：数据来源与接入、存储、业务接口、前端、AI、权限及运行维护的职责和连接，标清已实现与待验证部分。再在现有项目中跑通一条小而完整的实际链路，逐步增加功能；全图不要求提前写所有模块或生成空目录，也不保证今后职责细节永远不变。接入真实外部数据前需尽早核对最小样本，结构按证据演进。

理解卡点用当前实际数据展示中间值：数据库行、后端组织结果、HTTP JSON、Vue接收值及组件输入分别看清。需要日志时仅输出可公开的演示数据，真实数据和凭据不随意打印。提示按本次表现逐步减少：新机制局部示范、同类功能参考旧代码组织、再到依据目标选择修改位置；不机械按第几次接触判定独立，不给已掌握内容反复整段示范。

以一个完整、可使用的功能作为从开工到验收的任务，学生在实现这个功能的过程中学习。开工先展示数据、完整目标、涉及文件与调用关系；实现时遇到新的知识，再对照当前真实代码解释并继续完成原功能。讲解可以按理解分段，任务持续指向同一个终点；熟悉写法合并完成。局部示范只服务于正在实现的功能，避免另开示范接口、绕去练习一圈、再回来重写；必要支架明确标注，既有成果直接接续。

账户、净值、持仓和历史记录的持久来源在数据库，后端负责查询/校验/处理，Vue保留收到的数据副本与界面状态，组件接收并显示。演示数据放在后端或数据库对应位置；主页面不再并排维护一套写死资产样本。后端暂时返回固定数据时，接口契约和职责保持，明确数据库实现尚未接通。测试专用素材按测试用途隔离。

复杂部分可由教师准备可运行的最小支架或在正确位置留出明确缺口，注明教师贡献、当前限制及以后学习时机。保留学生组织核心功能的机会，新增层内能力时复用已稳定的调用关系。新结构/抽象由实际需求解释；当前用不到的模块先在全图说明，不提前生成大量空文件。已有阶段成果保留，当前项目沿用现有目录、组件和接口，不重开项目。

### 每个小目标怎样教

查询数据库前，先展示真实表名、列名、样本行和完整目标返回结构，说明每组字段归属；熟悉的字段映射由学生自己组织。围绕一个完整功能逐步补齐，新SQL机制可局部解释，不把同一完整目标拆成看不出联系的零散任务。

1. **每次教学先说明当前位置和目的。** 每次讲解、补讲、收到1后继续或布置任务，先用几句自然语言/短链路说明：正在实现什么功能，这一步为什么做，数据从哪里来，结果接下来交给谁，完成后在哪里看到变化。开新功能或改结构时给业务→保存→后端→Vue→组件全图；同一功能只简短标出本步，避免反复长篇复述。对照真实文件和函数说明当前已连通、尚未连通的部分，区分print到终端、return给请求方及Vue显示；章节编号只作辅助，教学始终围绕可见目标。
2. **先讲清新机制，再给改法。** 对照当前项目的完整具体输入，说明谁触发、判断依据、执行顺序、独立保存的状态及前后结果；明确哪个操作会执行、哪个不会自动执行，并解释原因。每次新增或修改代码时，逐句解释其作用、执行时机、输入、关键写法和结果；对已熟悉的部分可简洁，但不得省略未讲过的参数或API。名词解释或比喻后要落回实际代码，用一个例子完整走通。新API讲到本次够用的输入、返回值和调用位置；新旧写法并列时说明差异与取舍。一次默认一个新机制；熟悉同类字段合并完成，不反复重讲或机械拆行。
3. **明确交还任务。** 每次讲解或补讲后都重新说明“现在请你做什么、保存后应看到什么”。对已反复练过且学生愿意尝试的写法，只给目标、相关文件和少量提示，让学生先组织；新用法先在当前功能中解释、示范并带着完成，待学生理解、反复实践并愿意尝试时，再交还自主组织；同类变化用于自然验收，不在每个知识点后额外插入练习。任务不能只写“理解一下”或“继续”。
4. **读文件，再给足够的反馈。** 先说哪部分已经正确，再定位一个主要卡点。把“思路不清、语法不熟、文件没保存/服务没启动”区分开。按需逐级提示；若同一解释仍没懂，换成当前实际数据走一遍，不继续追加新概念。已有运行问题先定位到能继续学习。

每个小目标有明确结束点。完成时一句话说明“这部分完成，接下来做什么、为什么接得上”，再推进；阶段收尾按开课时公布的标准验收，发现必要缺口时先说明原因，可选美化/曲线/整理不临时变成必做。约40分钟是可休息的课段参考，学生愿意继续就进入下一课段，清楚标出边界。

### 能力检查与稳定执行

新技术先核对实际用途和本次必要前置。自然的小需求变化中，学生可以查旧代码、资料和使用AI，观察其能否选择修改位置、组织数据、解释执行、检查正常与一个相关边界，以及复现定位错误。教师给出核心答案就标提示/示范；AI生成的内容与学生做的判断/验证分别记录，不要求默写或全站完全独立后才推进。

数据库、写操作、身份、归属与模型失败从首次出现时做必要隔离检查和日志，不等到最后打磨才开始测试。一般显示/样式修改按实际风险验证，已有证据充分就停止额外测试。

当前v2.2路线为后续备课基线。1.4完成且已有首批两三课证据前，教师默认不主动再发起外部路线重评或重排；用户新要求或实际阻碍仍按事实处理。日常卡点优先调整解释、练习分量和提示，按试用证据复盘。模型变强先调整教师/AI分工与验证方法；技术或顺序更换写明需求、证据、成本和复用成果。每周十几小时与2027年10月投递目标是用户确认的规划输入，实际投入和岗位资格另按事实核对。

### 命名、诊断和修改边界

学生希望在日常代码中逐步培养专业习惯：结合当前任务主动指出命名、格式、边界检查、可读性和验证方面值得养成的小习惯，解释具体收益，区分错误、可靠性和风格选择；按影响分批建议，不用无关排版反复打断教学。

新看板使用清楚且一致的英文名称；首次准备时核对VS Code现有语法/类型诊断是否启用，普通英文拼写提示按需使用。SQL关键字、API名、属性名及调用不一致会影响语义或运行，发现即解释并修正。自定义函数名只要定义与引用一致，TypeScript通常不会因英文拼错而报错；类型检查和英文词典检查分开。

实际名称影响理解或引用时，做有范围的整理：学生先找定义和调用点，再统一修改并检查绑定。已有数据保留，不为排版和无关风格重做已完成阶段。

AI生成代码须能指出改动位置、数据流、预期效果和验证办法。核心业务逻辑用具体输入说明，教师检查的是理解与结果，不按手写行数或生成量评分。

### 验证方式与适用范围

| 标签 | 适合检查什么 | 报告写什么 |
| --- | --- | --- |
| 静态 | 名称、引用、结构、明显语法问题 | 检查的文件和发现 |
| 真实接口 | HTTP回复、数据库保存、权限拒绝、精度 | 请求、预期、实际结果及隔离数据范围 |
| 脚本集成 | 实际前端函数到后端的数据链路 | 使用的适配环境、真实服务和覆盖范围 |
| 实际页面 | 点击、显示、布局、宽窄窗口 | 实际操作和可见结果，截图只取真实页面 |
| 用户报告 | 用户观察到的页面或操作结果 | 明确来源是用户报告 |

这些是检查范围，不是通用高低排名：布局看页面，权限/事务/金额看对应测试；浏览器正常不能单独证明数据库和权限正确。选择足够覆盖当前风险的方法，验证充分后停止额外测试。

### 记录格式

日常收尾只记日期/有效分钟或未统计、精确停点、必要的一行帮助/验证和下一步；同一课段不按每条消息追加完整报告。阶段收尾再汇总下面的完整简报。第1章收尾选一次学生自己的说明或标图，直接对应“数据从哪来、经过谁、在哪显示”，已有自然证据可复用，允许看代码/资料。

阶段简报：成果及验证标签 / 理解证据 / 帮助程度 / 遗留问题 / 下一步。帮助1为未获教师关键提示、可查资料后自行组织并验证，2为局部提示后完成，3为逐步指导或完整示范后完成；说明教师/AI生成了哪些核心代码，以及学生实际做了什么。帮助等级概括本次任务，不把一次准确解释、运行成功或AI生成整段后粘贴判为独立掌握。

课时一行：日期 | 有效分钟或未统计 | 章/阶段 | 帮助1–3或待观察 | 成果/下一步。只用实际计时或学生报告，聊天跨度和消息数不当作投入时间。教学规划讨论另标规划，不计成学习课时。
